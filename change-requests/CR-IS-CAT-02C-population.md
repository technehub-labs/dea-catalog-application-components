## 1. Executive Summary

This CR is the third sibling in the 5-CR ISC catalogue programme. It establishes the P1 priority population of 5 architecturally foundational components across 5 of the 10 component domains (ISCC-01, ISCC-04, ISCC-05, ISCC-06, ISCC-07). The P1 population is the validation step for the 10-domain taxonomy established in CR-IS-CAT-02A. The P2 and P3 follow-on populations extend the catalog to the remaining 5 domains.

The P1 population is the validation step per G-09: catalogue completeness must be evidenced, not assumed. The coverage report at `docs/coverage-reports/p1-coverage-report.md` records the methodology, the inventory, the doctrine validation, and the deferred components.

The population is generated by the deterministic script at `scripts/generate_p1_population.py`. The script is the source of truth for P1 records; hand-editing is discouraged. The script is reproducible; running it twice produces the same output.

## 2. P1 Selection Methodology

The 5 P1 domains were selected by the following criteria:

1. **Foundational**: the domain is architecturally foundational to any information system.
2. **Cross-cutting**: the domain has cross-cutting concerns that affect multiple other domains.
3. **P1 priority**: the domain is in the P1 priority band of the IS Semantic Architecture programme (per the 5-CR programme template; the standing rule from 2026-10-18).

The 5 selected domains are:

| Code | Domain | Justification |
|---|---|---|
| ISCC-01 | Customer Experience | Foundational; the primary external interface |
| ISCC-04 | Core Operations | Foundational; the back-office substrate |
| ISCC-05 | Data and Analytics | Cross-cutting; powers all other domains |
| ISCC-06 | Integration | Cross-cutting; enables the other domains to interact |
| ISCC-07 | Security | Foundational; required by every other domain |

The remaining 5 domains (ISCC-02 Employee Experience; ISCC-03 Partner Integration; ISCC-08 Observability; ISCC-09 Development Platform; ISCC-10 AI Native) are deferred to P2 and P3 follow-on populations.

## 4. Doctrine on Overlapping Domains (Validation)

The 4 boundary doctrines from CR-IS-CAT-02A section 3.1 are validated by the P1 population:

1. **ISCC-07 vs ISCC-04 boundary**: the Identity Broker is correctly classified under ISCC-07 (security infrastructure); the Order Management System is correctly classified under ISCC-04 (back-office). The Identity Broker depends on the Order Management System at runtime (recorded in the metamodel `dea:executes` relationship in 02D); the classification is by primary purpose, not by dependency.
2. **ISCC-05 vs ISCC-04 boundary**: the Data Warehouse Platform is correctly classified under ISCC-05 (data platform); the Order Management System is correctly classified under ISCC-04 (operations). The Order Management System produces data that the Data Warehouse Platform ingests; the classification is by primary purpose, not by data flow.
3. **ISCC-06 vs other-domain boundary**: the API Gateway is correctly classified under ISCC-06 (integration); none of the other P1 components duplicate this. The API Gateway is the only IGC (Integration Component) in the P1 population that is the primary integration component; the Identity Broker is a secondary IGC.
4. **ISCC-10 vs all-other-domains boundary**: no P1 component is classified under ISCC-10 (AI Native). The AI-assisted components are deferred to the P3 follow-on population.

## 6. CI Requirements

CI MUST validate (per the 14 rules from CR-IS-CAT-02B):
- v2 ISC schema validation (rule 1: F-level assignment; rule 2: primary component-domain)
- README existence (rule 3)
- Composition edges reference registered component identifiers (rule 4)
- Composition edges use a registered relationship kind (rule 5)
- F0 contains at least one F1 (rule 8)
- F1 contains at least one F2 (rule 7)
- F2 may contain F3 and F4 (rule 6)
- No self-ancestor (rule 9)
- Acyclic composition tree (rule 10)
- Composition depth <= 6 (rule 11)
- README includes change history (rule 13)
- README references parent and child components (rule 14)

The existing `validate-entities.yml` workflow enforces rules 1-5 and 11 (from 02A taxonomy reference and 02B composition validation). The 02D PR extends `validate-entities.yml` with the additional rules.

## 7. Exclusions

The following component kinds are explicitly excluded from the P1 population:

- **IFC (Infrastructure Component)**: not in scope of this catalogue; the IFC records are migrated to a separate catalog (`dea-catalog-infrastructure-components`) in a follow-on CR-IS-CAT-02-IFC.
- **Vendor-specific component instances**: per G-12, no implementation-specific component becomes canonical merely because it exists in an application. Vendor-specific components are referenced through the metamodel `dea:executes` relationship in 02D; they do not appear as catalogue records.
- **Test components and ephemeral components**: not in scope of the canonical catalogue.

## 8. Acceptance Criteria

1. The 5 P1 domains are populated with F2 composite components.
2. Each F2 has 2-3 F4 sub-components (14 F4 total).
3. All 19 component records validate against the v2 ISC schema.
4. All 19 component records have a 19-section README.
5. The 14 composition edges are recorded in the v2 schema's `composition` array.
6. The 4 boundary doctrines are validated.
7. The catalog-level index reflects the P1 counts.
8. The 5 domain-level indexes reflect the P1 component lists.
9. The deterministic generator is reproducible.
10. The coverage report is generated and committed.
11. CI passes.

## 9. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Incomplete coverage | The P1 tranche covers 5 of 10 domains; the remaining 5 are deferred to P2/P3 follow-on populations (documented in the coverage report) |
| Doctrine violations | The 4 boundary doctrines are validated explicitly in section 4; the coverage report records the validation |
| Composition edge proliferation | The 4 relationship kinds (contains, depends-on, hosts, orchestrates) are the only authorized kinds; the composition edges are recorded in the v2 schema's `composition` array (rule 5) |
| Vendor-specific leakage | Per G-12, no implementation-specific component becomes canonical; vendor-specific components are referenced through the metamodel `dea:executes` relationship in 02D |
| Documentation decay | Every active component MUST have a README (rule 3); the README MUST include a change history (rule 13) |

## 10. Definition of Done

The P1 population is complete when the 5 P1 domains are populated, all 19 component records validate, the coverage report is generated, and CI passes. Per G-09, completeness is evidenced by the 02C population exercise; a populated domain is NOT automatically considered complete (the doctrine validation in section 4 is the additional check).
